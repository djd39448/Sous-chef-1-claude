## P0 — visible breakage of a primary workflow

### P0-1. "Add To Shopping List" timeout wipes the loaded plan
**Observed.** Tapped "Add To Shopping List" on the Plan tab. The button went
into "Creating list…". After ~30s the entire Plan view replaced itself with
a red error card titled "Couldn't load your meal plan." and body "Couldn't
create list: Network error: The request timed out." The plan rows were
gone. Tapping "Try again" reloaded the original plan correctly — so the
plan was never destroyed, just hidden by the error state.

**Where.** [PlanScreen.swift:577](ios/SousChef/Screens/PlanScreen.swift):
```swift
catch {
    loadState = .failed("Couldn't create list: \(error.localizedDescription)")
}
```
This catch replaces the entire `loadState`, which makes the rest of the
screen render its error case (whose header reads "Couldn't load your meal
plan." — also misleading: the *plan* loaded fine; the *shopping list*
didn't).

**Fix sketch.** Don't store shopping-list errors on `loadState`. Add a
separate `@State var shoppingListError: String?` and render it inline next
to the shopping-list button. Leave `loadState.loaded(plan:)` untouched on
failure.

### P0-2. `generate-shopping-list` times out for a fresh 7-day plan
**Observed.** Same trigger as P0-1: tapping "Add To Shopping List" with a
fresh 7-day plan never returned within 60s.

**Where.** The backend handler at
[handlers_shopping.go:270](backend/internal/api/handlers_shopping.go:270)
calls `s.ai.ChatJSON` against `gpt-4.1` for the full shopping list — that's
a single non-streaming completion that has to emit 30–60+ items. iOS's
default `URLSession.shared.data(for:)` request gives ~60s before timing out.

**Fix sketch.** Two pieces. (a) Lift the iOS request timeout for this
endpoint (e.g. a dedicated `client.post(... timeout: 180)` variant, or set
`req.timeoutInterval` on the underlying URLRequest). (b) On the backend,
either switch the shopping-list generation to streaming (mirrors the
recipe-stream pattern, lets the iOS client render items as they arrive) or
fire it as a background goroutine with a poll-for-ready endpoint, same
shape as the eager image-gen pattern we just shipped.

## P1 — wrong content / wrong state, less catastrophic

### P1-1. Same dish gets two different AI photos (meal-plan-day vs cookbook)
**Observed.** Wed 27's Korean Veggie Bibimbap on Plan has one photo (bowl
with mushrooms + greens). Opening the recipe auto-saves to Cookbook. The
Cookbook tile for the same dish shows a *different* photo (bowl with
sprouts + cucumber). Both are valid bibimbap photos but they don't match,
so the same dish appears to be two different recipes.

**Where.** Two independent image-gen calls run:
- `handleGenerateMealPlan` → `kickoffMealDayImages` persists on
  `meal_plan_days.image_url`.
- `handleCreateCookbookRecipe` (or `toolSaveRecipe`) →
  `kickoffCookbookImage` persists on `cookbook_recipes.image_url`.

Each call to `gpt-image-1` is non-deterministic, so they diverge.

**Fix sketch.** When the auto-save path runs from `streamGenerate`, copy
the day's already-persisted `image_url` into the cookbook row instead of
firing a fresh image generation. The iOS `saveToCookbook` body could carry
an optional `imageUrl: meal.imageUrl` and the backend's
`handleCreateCookbookRecipe` would prefer that over the helper's image-gen
call. Saves a `gpt-image-1` call and gets the photos to match.

### P1-2. Bookmark on a re-opened meal-plan recipe doesn't reflect its saved state
**Observed.** Reproduce manually (didn't trigger in this run, but the code
path is obvious): generate a recipe → auto-save fires → close the
fullScreenCover → re-open the *same* day's recipe. `RecipeScreen.saved`
initializes to `false`. `load()` sees `recipeContent` is non-empty so it
short-circuits — `streamGenerate` (and its auto-save tail) never run. The
bookmark icon shows unfilled. Tapping it manually creates a *duplicate*
cookbook row for the same recipe.

**Where.** [RecipeScreen.swift load()](ios/SousChef/Screens/RecipeScreen.swift)
and `@State private var saved = false`.

**Fix sketch.** Either (a) check at load time whether the user already has
a cookbook recipe with this title and set `saved = true` if so — needs a
new lightweight endpoint, e.g. `GET /api/kitchen/cookbook?title=...`. Or
(b) backend-side, have `handleCreateCookbookRecipe` dedupe on
`(user_id, title)` — return the existing row instead of inserting a
duplicate. Pair it with a uniqueness index on `cookbook_recipes (user_id,
lower(title))`. Option (b) is simpler and protects against future double-
save bugs from any caller.

### P1-3. Cookbook with one recipe shows the same tile twice
**Observed.** Cookbook tab with a single saved recipe shows it both as the
big "LAST SAVED" featured card AND as the lone grid tile beneath. Reads
as two recipes until you tap and realize they're the same.

**Where.** [CookbookScreen.swift](ios/SousChef/Screens/CookbookScreen.swift)
— the featured card and the grid both pull from the same list with no
"skip the featured row in the grid" logic.

**Fix sketch.** Skip the featured recipe from the grid: `recipes.dropFirst()`
when search is empty (search-active view already hides the featured card,
so the grid stays whole there). Mirrors the original web-app behaviour
where the featured = "most recent" and the grid = "the rest."

### P1-4. Past Lists sheet renders with side gutters
**Observed.** Tap the filter/list icon on the Shopping tab (when no list
yet) → "Past Lists" sheet opens. The sheet's interior renders with two
beige vertical strips on the left and right of a narrower white column.
Title "Past Lists" centers in the white column; "Done" pill in the right
beige gutter. Looks like a width-constraint bug rather than intentional
design.

**Fix sketch.** Find the sheet view and confirm its root uses
`.frame(maxWidth: .infinity)` and that its background extends edge-to-edge.
A `Form` or `List` inside a custom container is the usual culprit.

## P2 — UX polish / lower-impact

### P2-1. Sign-in: Apple and Google buttons mislead
The big "Sign in with Apple" and "Continue with Google" buttons both open
the same email/password sheet (per the SIWA-deferred CHANGE_LOG entry).
A new user reads these as native auth flows. Either wire SIWA / Google
properly, or label the buttons "Sign in with email" / hide them until the
real flows land.

### P2-2. Sign-in screen: AI KITCHEN PARTNER badge overlaps the food photo's bottom edge
The pill sits half-on-half-off the bottom edge of the hero food image,
reads as an accidental bleed rather than an intentional sticker.

### P2-3. Email sign-in sheet is bare
No "Show password" toggle. No "Forgot password?" link. "Need an account?
Create one" is the only secondary action.

### P2-4. Three different surfaces use the `filter` icon as a placeholder
- Calendar Week-vs-Month toggle (Week slot uses `filter`)
- Shopping tab top-left ("Past Lists" trigger)
- Chat tab top-left ("History" trigger)

The `filter` SF Symbol (`line.3.horizontal.decrease`) doesn't communicate
"history" or "list" — it reads as filtering. Swap each for an icon that
matches its action (`list.bullet`, `clock.arrow.circlepath`, etc.).

### P2-5. Shopping tab empty state has no actionable button
"No shopping list yet." / "Ask Sous Chef to build one from your plan."
There's nothing tappable beyond the `+` (manual add) and the filter (past
lists). User has to know to navigate to Plan and tap "Add To Shopping
List." Add a primary button — either "Generate from this week's plan" (if
a plan exists, fire `/generate-shopping-list`) or "Plan a Week First"
(jump to Plan tab).

### P2-6. Home tonight card's notes wrap awkwardly next to the meta pill row
The notes ("30 minutes – Sautéed chicken with lemongrass, garlic, …")
wrap to a narrow column on the left while "Serves 4 · Easy" pillars on
the right, producing a tall, broken-looking text block. Consider showing
the notes on their own line beneath the meta row.

### P2-7. "Approve all 7 days to finalize" sits as a dimmed CTA in edit mode
Reads like the primary action until you realize it's only enabled when
every checkbox is ticked. Either restate as an instructional label
("Tap a meal to keep it, then…") and put the real CTA in a dedicated
button, or hide entirely until all-checked.

### P2-8. Edit-mode CTA confusion: my tap on "Regenerate Unchecked" probably hit "Add To Shopping List" through layout shift
In edit mode the regenerate / finalize buttons appear just above the
("Add To Shopping List") sage card. After the rows reflow as the user
checks items, the regenerate button's screen position can move under
where the user's finger was — a single tap can land on the wrong target.
Hard to reproduce reliably; suggests inserting extra clearance between
the edit-mode footer and the shopping CTA, or moving the shopping CTA
behind a separate scroll boundary while edit mode is active.

### P2-9. Cookbook search field — keyboard handling
This may be sim-only: long-pressing 'a' in the simulator pops the accent
picker and eats subsequent characters. On a real device this is unlikely
to bite. Worth a quick check that the field has `.autocorrectionDisabled`
configured cleanly and that the `x`-to-clear button doesn't get covered
by the keyboard's autocorrect bar.

### P2-10. Empty-week-strip placeholder on Home shows only 3 cards
On a fresh account before plan generation, "This Week" shows 3 dash
placeholder cards in a horizontal scroll. Should be 7 (so the empty
shape matches the populated shape). HomeScreen builds them via
`ForEach(0..<7, id: \.self)` already, so it's likely a scroll-clip issue
rather than an off-by-7 — see how many actually render at small widths.

## What I think to fix first

1. **P0-1 + P0-2 together.** The shopping-list timeout is the single
   biggest UX hole in the current build, and the recovery-with-wiped-plan
   makes it scary. Either split error state and lengthen the timeout,
   or move shopping-list-gen to streaming/background like image-gen.
2. **P1-1.** Two-photos-for-one-dish reads as a bug even though both photos
   are "fine" individually. Cheapest fix: reuse the day's image_url for the
   cookbook row on auto-save.
3. **P1-2 + P1-3.** Cookbook dedupe + "skip featured in grid" — both small
   surgical changes that clean up a real-user pattern (open the same recipe
   twice).
